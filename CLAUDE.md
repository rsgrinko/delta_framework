# CLAUDE.md

Этот файл содержит инструкции для Claude Code (claude.ai/code) при работе с кодом в этом репозитории.

## Обзор проекта

Delta Framework — собственный, самописный PHP-фреймворк (не построен на Laravel/Symfony/и т.п.). Код, комментарии и
сообщения коммитов преимущественно на русском языке. Нет системы сборки фронтенда (нет npm/webpack) — публичный сайт
использует серверный рендеринг шаблонов Twig с самописной CSS-дизайн-системой, админ-панель использует обычные
страницы PHP/jQuery.

## Команды

```bash
# Установка зависимостей
composer install

# Юнит-тесты (без базы)
vendor/bin/phpunit --testsuite unit

# Интеграционные тесты (нужен config.local.php с реквизитами базы;
# создают и удаляют собственные таблицы с префиксом test_)
vendor/bin/phpunit --testsuite integration

# Запуск отдельного файла теста / метода
vendor/bin/phpunit tests/Integration/AuthTest.php
vendor/bin/phpunit --filter testLegacyPasswordIsRehashedOnLogin

# Миграции базы данных (Phinx, конфиг в phinx.php, миграции в db/migrations, сиды в db/seed)
vendor/bin/phinx migrate -e dev
vendor/bin/phinx migrate -e prod
vendor/bin/phinx seed:run -e dev

# Быстрая проверка синтаксиса/рендера без браузера (иначе нет тестового окружения, рендерящего Twig):
php -l core/lib/Core/App.php
php -r '$root="."; require $root."/vendor/autoload.php"; $t=new Twig\Environment(new Twig\Loader\FilesystemLoader($root."/templates"),["strict_variables"=>false]); echo $t->render("index.twig", [...]);'
```

Локального скрипта dev-сервера нет — это классическое приложение nginx + PHP-FPM. **`.htaccess` в этом проекте
не работает вообще:** dev-хост обслуживается nginx (openresty), перенаправление на `index.php` задано в конфиге
веб-сервера, а `uploads/.htaccess` не читается и загруженные файлы от исполнения не защищает. В реальном dev-окружении этого проекта правки на диске автоматически
синхронизируются с работающим хостом `dev.it-stories.ru` — этот хост полезен для сквозной проверки поведения
(например, через `curl` с cookie jar для проверки POST-сценариев с авторизацией по сессии), когда что-то нельзя
подтвердить только по коду.

## Архитектура

### Точки входа
- `index.php` — устанавливает `USE_ROUTER = true` и подключает `core/bootstrap.php`. Это единственная точка входа
  для публичного сайта (все запросы переписываются сюда, затем диспетчеризуются роутером).
- `core/api.php` — точка входа REST API. Диспетчеризует вызовы к методам `Core\Api\ApiController` по
  `$_REQUEST['method']`, аутентифицирует через `$_REQUEST['token']` по `User::getByToken()`, за исключением методов,
  перечисленных в `$noAuthMethods` (включает `createUser`/`getToken`, поэтому создание аккаунта и получение токена по
  логину работают без авторизации).
- `core/cron.php` — сканирует `core/cronTasks/*.php` (кроме `init.php`) и запускает каждый через `exec()` как
  отдельный фоновый PHP-процесс. Это механизм для плановых/фоновых задач, а не библиотека планировщика.
- `admin/index.php` и соседние файлы (`admin/users.php`, `admin/posts.php` и т.д.) — админ-панель представляет собой
  отдельный набор обычных PHP-страниц (не маршрутизируется через `core/routes.php`), использующих общие
  `admin/inc/bootstrap.php`, `header.php`, `footer.php`. AJAX-обработчики находятся в `admin/ajax/`.

### Порядок бутстрапа и загрузки конфигурации (`core/bootstrap.php`)
1. `vendor/autoload.php` (Composer PSR-4: `Core\` → `core/lib/Core/`) — единственный механизм автозагрузки
2. `config.local.php` в корне проекта, если он присутствует — хранилище секретов и переопределений окружения
   (вне git). Также это механизм для запуска нескольких сайтов на одной кодовой базе.
3. `Config::boot(config/)` — сборка конфигурации, затем `core/config.php` публикует её значения в виде
   legacy-констант, каждая под `if (!defined(...))`, чтобы `config.local.php` сохранял приоритет.
4. Регистрируется `Delta\Error\ErrorHandler` — центральный обработчик исключений, ошибок и фатальных завершений.
   Всё пишется в `core/log/error.log.php`; наружу при `DEBUG` уходит трассировка, иначе — страница 500.
5. Если `CORE_FULL_LOAD` (т.е. это не cron-процесс) и `USE_ROUTER === true`: инициализируется Twig
   (`PATH_TO_TEMPLATES` = `/templates`), создаётся `Delta\Routing\Router`, подключается `core/routes.php`,
   и `Delta\Http\Kernel::handle(Request::capture())->send()` превращает запрос в ответ.

`IS_CRON_PROCESS` (если определена как true до бутстрапа) отключает UTM-трекинг, обработку сброса кэша/логаута и
настройку DDoS-защиты — cron-задачи подключают `bootstrap.php` с этим флагом.

### HTTP-ядро (`src/Http`, `src/Routing`)
Запрос превращается в ответ ровно в одном месте — `Delta\Http\Kernel::handle(Request): Response`.

- `Delta\Http\Request` собирается из суперглобалей через `Request::capture()`. Дальше по коду обращаться к
  `$_GET`/`$_POST`/`$_FILES` не нужно: есть `query()`, `post()`, `input()`, `string()`, `integer()`, `file()`,
  `header()`, `isAjax()`, `isPost()`, атрибуты маршрута.
- `Delta\Http\Response` — статус, заголовки и тело; отправляется единственным `send()` в точке входа.
  Фабрики: `Response::html()`, `json()`, `redirect()`, `notFound()`.
- `Delta\Http\UploadedFile` — **единственная точка валидации загрузок.** Расширение выводится из реального
  MIME-типа содержимого (`finfo`), а не из имени файла, присланного клиентом. Пользовательские загрузки
  сохраняются только через `File::saveUploadedFile()`; `File::saveFile()` — для файлов, уже лежащих на диске.
- `Delta\Routing\Router` — экземплярный, не статический. `$router->route($pattern, $handler, $usePagination)`,
  сопоставление по `Request::path()` (строка запроса отброшена). Не совпавшие маршруты уходят на `/404`.
- В `src/Routing/Router.php` намеренно **не** включён `strict_types`: параметры маршрута всегда строки, а
  легаси-обработчики объявляют их как `int`; strict-режим действует на месте вызова и ломал бы такие вызовы.

- `Delta\Http\Pipeline` + интерфейс `Delta\Http\Middleware` — сквозное поведение выносится из контроллеров.
  Список middleware задаётся в `core/bootstrap.php` при создании `Kernel`; сейчас в нём `CsrfMiddleware`.
  Любой middleware может прервать цепочку, вернув ответ вместо вызова `$next`.

**Обработчик маршрута может быть двух видов.** Новый стиль возвращает `Response`. Старый стиль печатает в вывод и
сам зовёт `header()` — маршрутизатор перехватывает вывод буферизацией и оборачивает в `Response`. Это сделано
намеренно, чтобы переводить маршруты на новый стиль по одному. Все маршруты `core/routes.php` пока в старом стиле.

Контроллер по умолчанию для маршрутов сайта — `Core\App` (`core/lib/Core/App.php`); его приватный `render()`
объединяет специфичные для страницы переменные шаблона с общими переменными макета из `getLayoutParams()` (статус
авторизации, текущий пользователь + аватар, использование памяти/времени, непрочитанные сообщения и т.д.) перед
передачей в Twig.

Группы маршрутов помимо очевидных CRUD-подобных:
- `/dialog/(\d+)/messages` (GET) — JSON-эндпоинт, возвращающий свежесгенерированный HTML-фрагмент списка сообщений +
  счётчики, используется как AJAX-отправкой в `chat.js`, так и его циклом опроса (см. раздел "Фронтенд" ниже).
- `/profile`, `/profile/personal`, `/profile/password`, `/profile/avatar`, `/profile/resend-verification` — раздел
  самостоятельного управления настройками аккаунта (методы `App::profile*`), все работают по схеме
  POST-и-редирект-обратно-на-`/profile` с одноразовым флеш-сообщением, хранящимся в `$_SESSION['profileMessage']`.

### Слой базы данных (`Core\Database\DataBase`)
Синглтон-фасад (`DataBase::getInstance($driver)`), оборачивающий реализацию `DatabaseDriverInterface`, выбираемую в
конструкторе через `match` по имени драйвера (на данный момент только `'mysql'` → `Core\Database\Drivers\MySqlDriver`;
структура `match` предназначена для добавления других драйверов в `core/lib/Core/Database/Drivers/`). Фасад
предоставляет `query`, `add`, `update`, `delete`, `get`, `getList`, `getCount`, а также методы транзакций
(`startTransaction`/`commitTransaction`/`rollbackTransaction`), все делегируют вызовы драйверу. Имена таблиц по всей
кодовой базе имеют префикс `DB_TABLE_PREFIX` (например, `Core\Models\MQ::TABLE = DB_TABLE_PREFIX . 'threads'`).

`MySqlDriver::update()`/`delete()` на практике всегда возвращают `false` (они определяют успех по `fetchAll()` для
не-SELECT запроса, который всегда пуст) — не стоит ветвиться по возвращаемому значению `DataBase::update()`;
единственный надёжный сигнал ошибки — выброшенное исключение `DatabaseException`. Известный спящий баг: ключ
инвалидации кэша в `User::update()` не совпадает с ключами, под которыми `User::getAllUserData()` реально кэширует
данные (в нём отсутствует компонент флага `onlySecureData`), поэтому кэшированные данные пользователя никогда
корректно не инвалидируются при записи — сейчас это безвредно, поскольку `USE_CACHE` по умолчанию выключен, но
проявится в виде устаревших данных (устаревший пароль/email/и т.д. через `getLogin()`/`getEmail()`/`getAllUserData()`),
если кэширование когда-либо включат. Чинится выравниванием формата ключа кэша в `update()` с форматом в
`getAllUserData()`.

### Структура базы данных (`delta`, MySQL)
База содержит 24 таблицы. Внешних ключей (`FOREIGN KEY`) в базе нет вообще — все связи между таблицами (`user_id`,
`dialog_id` и т.п.) обеспечиваются только на уровне кода, а не средствами СУБД.

Таблицы приложения (префикс `d_` = `DB_TABLE_PREFIX`):
- `d_users` — пользователи: `login` уникален, есть индекс по `token`; `last_active` хранится как `varchar`, а не
  `datetime`/`timestamp`.
- `d_roles` / `d_user_roles` — роли и их назначение пользователям.
- `d_user_meta` — произвольные атрибуты пользователя в формате ключ/значение.
- `d_dialogs` / `d_messages` — личные сообщения (диалоги и сами сообщения).
- `d_posts` / `d_sections` — контент и разделы (CMS).
- `d_files` — метаданные загруженных файлов.
- `d_utm_history` — история UTM-меток.
- `d_mail_history` — история отправленных писем (~1.5 МБ).
- `d_threads` / `d_threads_history` — таблицы очереди задач (MQ), используемые панелью "Менеджер очереди" в
  админке. `d_threads_history` — самая большая из "рабочих" таблиц: **315 469 строк / ~27 МБ** на момент анализа
  (2026-07-24) — похоже, никогда не чистится/не архивируется.
- `d_ddos_protection`, `d_phinxlog`, `d_migrations` — служебные/инфраструктурные таблицы.

Таблицы без префикса `d_` (не по общей конвенции именования, судя по всему из отдельных cron-скриптов/парсеров
контента):
- `podslyshano` — 64 738 строк, ~71 МБ — самая большая таблица во всей базе.
- `spider` — 1889 строк, ~47 МБ; есть индекс `text_index` по колонке `text` (обычный `MUL`, не `FULLTEXT` — стоит
  проверить, не подразумевался ли полнотекстовый индекс).
- `bashorg`, `jokes`, `myslo` — небольшие таблицы, похожи на парсеры шуток/цитат.
- `test__table`, `test__table2` — пустые таблицы на движке MyISAM, похожи на мусор/остатки экспериментов,
  кандидаты на удаление.

### Модели (`core/lib/Core/Models/`)
Обычные классы (не ORM), оборачивающие вызовы `DataBase` по функциональным областям:
- `User`/`UserModel`/`UserMeta` — авторизация, профиль, присутствие. `isOnline($id)`/`getOnlineCount()` вычисляют
  присутствие по `last_active` + `USER_ONLINE_TIME`; `last_active` обновляется только как побочный эффект
  `isAuthorized()` (в обеих её ветках — и куки-, и сессионной). `changePassword()`/`changeEmail()` — это
  self-service версии, используемые в `/profile` (в отличие от `resetPassword()`, которая принудительно
  генерирует и отправляет по почте случайный пароль). **Подводный камень:** `changePassword()` должна обновить
  `$_SESSION['password']` после успешной смены пароля, иначе проверка согласованности сессии в `isAuthorized()` на
  самом следующем запросе (которая сравнивает двойной хэш текущего пароля из БД с хэшем, захваченным при логине)
  молча разлогинит пользователя — это именно тот баг, который на *следующей* попытке выглядит как "неверный
  текущий пароль", хотя таковым не является.
- `Dialog` — личные сообщения; `getLastMessage($dialogId)` формирует превью в стиле "входящие" для списка диалогов.
- `Posts`, `Roles`, `File`, `UTM` (сбор UTM-меток, выполняется на каждом полном запросе) и `MQ`/`MQResponse`
  (очередь задач/исполнитель на основе БД, используется панелью "Менеджер очереди" в админке и `MQTasks.php`).
- `Core\DataObjects\AbstractModel`/`AbstractCollection`/`ModelCollection` предоставляют лёгкую базу для поведения
  моделей/коллекций, используемую более новыми моделями.

### Фронтенд (`templates/`, `assets/`)
Серверный рендеринг Twig, единый общий макет, никакого клиентского фреймворка или шага сборки.
- `templates/layout.twig` — это каркас страницы: центрированная "карточка" (`.shell`) с градиентным
  хедером/футером и иконочной навигацией, плавающая на простом фоне страницы — не full-bleed интерфейс приложения.
  Каждая страница рендерится внутри `.shell-content`.
- `templates/_icons.twig` содержит все иконки в виде Twig-макросов, выводящих инлайновый SVG (без иконочного шрифта,
  без CDN). **Импортируйте его в каждом шаблоне** — `{% import '_icons.twig' as icons %}` в начале *каждого*
  шаблона, использующего `icons.xxx()`, поскольку импорты Twig не наследуются от родительского шаблона через
  `{% extends %}`.
- `assets/css/style.css` — единая самописная таблица стилей, использующая CSS custom properties (дизайн-токены в
  `:root`: цвета, радиусы, тени, `--gradient-brand`, используемый повсюду для основных акцентов). Переиспользуемые
  классы компонентов: `.page-head` (заголовок страницы + иконка), `.section`/`.section-title` (группировка
  контента — намеренно *не* отдельный блок с рамкой, чтобы избежать вида "карточка внутри карточки", раз `.shell`
  уже обрамляет страницу), `.info-list` / `.meta-grid` (отображение ключ/значение), `.status` +
  `.avatar-wrap`/`.avatar-status-dot` (точка присутствия онлайн/офлайн поверх аватара), `.pill`/`.nav-badge`
  (счётчики), `.dialog-list`/`.dialog-row` (строки списка в стиле мессенджера). При добавлении нового
  панелеподобного UI-элемента избегайте собственных `border`/`box-shadow`, если он уже находится внутри
  `.shell-content` — это регулярно повторяющаяся ошибка, дающая эффект "окна внутри окна".
- Диалоги/чат (`dialog.twig`, `dialogs.twig`, `templates/_messageList.twig`, `assets/js/chat.js`): разметка списка
  сообщений (группировка последовательных сообщений от одного отправителя, разделители по дням, рендеринг по типам
  для text/image/file) находится ровно в одном месте, `_messageList.twig`, который рендерится как при обычной
  полной загрузке страницы, так и отдельно, через `App::outputDialogJson()`, для AJAX-ответов — следует сохранять
  это, а не дублировать логику рендеринга в JS. `chat.js` обрабатывает AJAX-отправку (`FormData`, без полной
  перезагрузки страницы), авто-изменение размера textarea, отправку по Enter (Shift+Enter для новой строки) и
  опрашивает `/dialog/(\d+)/messages` каждые несколько секунд на предмет новых сообщений, прокручивая вниз заново
  только если пользователь уже был проскроллен близко к низу.
- Аватары: изображения на основе `File` опциональны для каждого пользователя — каждое место, рендерящее аватар
  (навигация, список диалогов, шапка чата, профиль), должно обрабатывать случай "нет `image_id`" через запасной
  вариант — бейдж с буквой инициала; см. любой существующий блок
  `{% if x.avatar %}...{% else %}...{% endif %}` для образца (и используйте `name|default(login)`, а не
  `nameForDisplay`, для инициала — последнее является отформатированной строкой `"[id] (login) name"`).

### Хелперы (`core/lib/Core/Helpers/`)
Сквозные утилиты: `Cache` (файловое хранение, управляется `USE_CACHE`/`CACHE_DIR`/`CACHE_TTL`, инициализируется
один раз в бутстрапе), `Log`, `Mail`, `Captcha`, `DDosProtection` (базовое ограничение частоты запросов по
`USE_DDOS_PROTECTION`), `Registry` (простое статическое хранилище ключ/значение, используемое, например, для
хранения текущего callback маршрута), `Sanitize`, `Files`, `Thumbs`, `Zip`, `SystemFunctions`, `Pagination`
(`execute()`/`getLimit()` вычисляют смещение для SQL `LIMIT`; геттеры `getPage()`/`getTotalPages()` существуют для
рендеринга элементов управления пред./след. — вызывайте `execute()` перед любым из геттеров).

### Внешние сервисы (`core/lib/Core/ExternalServices/`)
Тонкие клиенты для Telegram (`Telegram`, `Telegram2`, `TelegramSender`, `TelegramActions` — обратите внимание, есть
параллельные/устаревшие варианты, проверяйте, какой реально подключён, прежде чем расширять), `ChatGPT`,
а также пара HTTP `Request`/`RequestOLD` (для нового кода предпочитайте `Request/`, а не вариант OLD).

### Конфигурация
Источник истины — объект `Delta\Config\Config` и PHP-файлы каталога `config/` (`app`, `database`, `cache`, `mail`,
`telegram`, `security`). Имя файла — корневой ключ, доступ по точечной нотации: `$config->get('database.host')`.
Экземпляр собирается в `core/bootstrap.php` через `Config::boot()` и подменяется в тестах через
`Config::setInstance()`.

Значения внутри `config/*.php` читаются через `Delta\Config\Env::get()` с фиксированным порядком поиска:
переменная окружения → одноимённая глобальная константа (так подхватывается `config.local.php`) → значение по
умолчанию.

`core/config.php` больше не хранит настройки — это слой совместимости, публикующий значения `Config` в виде
прежних глобальных констант (`DB_HOST`, `CACHE_*`, `TELEGRAM_*` и т.д.), потому что на них опирается
существующий код. **Новый код должен использовать `Config`, а не константы.** `Core\SystemConfig::getValue($name)`
тоже переведён на `Config`: он транслирует имя legacy-константы в точечный ключ.

Окружение задаётся `APP_ENV` (`local`/`dev`/`prod`) и `APP_DEBUG`; от них зависят вывод ошибок и режим Twig.
Файл `.env` намеренно не используется до переноса docroot в `public/`: сейчас корень проекта совпадает с корнем
сайта, а веб-сервер отдаёт любой файл не с расширением `.php` сырым текстом — `.env` читался бы прямо по URL.

**Секреты живут только в `config.local.php`** (в корне проекта, вне git; шаблон — `config.local.example.php`):
реквизиты БД, токен Telegram-бота, `CRYPTO_KEY`, а также реквизиты окружений Phinx. В `core/config.php` для них
оставлены пустые значения по умолчанию, и при отсутствии реквизитов БД приложение падает сразу с понятным
текстом. Не добавляйте новые секреты в отслеживаемые файлы. Учтите, что старые значения остались в истории git
и должны считаться скомпрометированными.

### Тестирование
Конфигурация — `phpunit.xml`, загрузчик — `tests/bootstrap.php`. Два набора:

- **`--testsuite unit`** — не обращается к базе, запускается где угодно.
- **`--testsuite integration`** (`tests/Integration/`) — работает с **настоящей** базой. Реквизиты берутся из
  `config.local.php`, но префикс таблиц переопределяется на `test_`: тесты создают собственные таблицы
  `test_users`, `test_roles` и т.д. в той же базе и удаляют их после прогона, рабочие данные не затрагиваются.
  Без `config.local.php` набор пропускается. Схема — `tests/Support/TestDatabase.php`; **при изменении рабочей
  схемы её нужно синхронизировать там же.** Префикс обязан определяться до загрузки классов ядра: имена таблиц
  вычисляются в константах классов при первой загрузке файла.

Покрыты сценарии входа (включая приём старых md5-хешей и их миграцию) и личного кабинета (смена пароля,
согласованность сессии, роли). Статического анализа в проекте нет — Psalm удалён.
Целевая версия PHP — 8.4 (`composer.json`), на ней же работает dev-хост; локальный `php` в PATH может быть
старее, для прогонов используйте интерпретатор 8.4. Автоматического
покрытия тестами маршрутов/шаблонов нет — при изменении контроллеров `App.php` или шаблонов Twig делайте
проверку через `php -l` плюс одноразовый рендер Twig (см. раздел "Команды" выше), прежде чем считать изменение
завершённым, и предпочитайте проверять сессионно-зависимые сценарии (логин, смена пароля, AJAX-эндпоинты) на живом
хосте синхронизации `dev.it-stories.ru` через `curl` с cookie jar, а не гадать по одному только коду.

## Известные проблемы безопасности и качества (аудит 2026-07-29)

Ниже — конкретные, проверенные по коду находки (не гипотезы), отсортированные примерно по критичности. При работе
в затронутых областях учитывайте это и по возможности предлагайте исправление, а не тиражируйте паттерн дальше.

- ~~**Неограниченная загрузка файлов → потенциальный RCE.**~~ Закрыто на Этапе 3. Все пользовательские загрузки
  (вложение в диалоге, аватар в профиле, аватар в админке) идут через `File::saveUploadedFile()`, который
  проверяет тип и размер и выводит расширение из реального MIME-типа содержимого. Прежняя «защита»
  `uploads/.htaccess` не работала вообще: сервер — nginx, `.htaccess` он не читает. `File::saveFile()` оставлен
  только для файлов, уже лежащих на диске, и **не должен** использоваться для данных из HTTP-запроса.
- ~~**Слабое хеширование паролей.**~~ Закрыто на Этапе 5. `Delta\Security\PasswordHasher` использует
  `password_hash()` (bcrypt): своя соль у каждой записи. Старые md5-хеши продолжают приниматься при входе и
  **прозрачно перехешируются в bcrypt при первом же успешном входе** (`User::rehashIfNeeded()`), поэтому сброс
  паролей не нужен. Поиск пользователя по хешу пароля больше невозможен — везде сначала выборка по логину,
  затем `User::verifyPassword()` (так переписаны `securityAuthorize()` и `ApiController::getToken()`).
  Отпечаток сессии — `User::sessionFingerprint()`, токен автологина — `authCookieToken()` на `hash_hmac`.
- ~~**Нестрогое сравнение хешей (`==`).**~~ Закрыто на Этапе 5: сверка cookie-токена и отпечатка сессии идёт
  через `hash_equals()`. Коды верификации больше не выводятся из статической соли (она утекла в историю git),
  а генерируются через `random_bytes()`.
- ~~**Cookies авторизации без флагов безопасности.**~~ Закрыто на Этапе 4: `User::setAuthCookie()` /
  `forgetAuthCookie()` выставляют `HttpOnly`, `SameSite=Lax` и `Secure` (последний — только на HTTPS, иначе
  cookie не установится на локальном HTTP). Отдельных вызовов `setcookie()` для авторизации в коде больше нет.
- ~~**Отсутствие CSRF-защиты.**~~ Закрыто на Этапе 4: `Delta\Security\Csrf` (синхронайзер-токен в сессии,
  сверка через `hash_equals`) + `CsrfMiddleware` в конвейере ядра. Токен доступен в шаблонах как глобальная
  Twig-переменная `csrfToken` и добавлен во все формы сайта. **Любая новая форма обязана содержать
  `<input type="hidden" name="_token" value="{{ csrfToken }}">`**, иначе POST вернёт 419. Для запросов из
  JavaScript без формы токен принимается из заголовка `X-CSRF-Token`.
- **Корень проекта = docroot.** Любой `*.php` в корне исполняется веб-сервером, а любой файл **не** на `.php`
  отдаётся сырым текстом (проверено). Не кладите в корень скретч-скрипты и файлы конфигурации, отличные от
  `config.local.php`. Устранено на Этапе 0: посторонние dev/test-файлы (`test.php`, `testMvc.php`, `testWait.php`,
  `webApp.php`, `meshtasticForward.php`, `composer.phar`) удалены, `admin/phpcmd.php` — веб-консоль выполнения
  произвольного PHP-кода — удалена вместе с мёртвым шаблоном `templates/index_lll.twig`.

## Архитектурные проблемы (аудит 2026-07-29)

Ниже — структурные проблемы, проверенные по коду (файл/строка), а не гипотезы. В отличие от раздела выше, это не
уязвимости, а то, что усложняет сопровождение, тестирование и безопасное внесение изменений.

- **`App.php` — God object-контроллер.** 490 строк, 24 метода, ни одного разделения на Controller/Service/
  Repository — методы напрямую мешают HTTP (`$_REQUEST`, `header('Location: ...')`), сессию (`$_SESSION`), файлы и
  БД в одном теле. Например `profileUpdateAvatar()` (374-458) в одном методе валидирует MIME присланного файла,
  сохраняет его на диск через `File::saveFile()`, обновляет пользователя в БД и пишет flash-сообщение в
  `$_SESSION`; `sendMessage()` (176-208) сам решает, AJAX это или обычный POST, ветвит текст/файл, и либо отдаёт
  JSON, либо делает редирект. При правке любого из этих методов следует по возможности выделять валидацию/бизнес-
  логику в модель, а не расширять и так перегруженный метод контроллера.
- **Модели — Active Record, местами со встроенной работой с сессией/куками.** Все модели в `Models/` — это
  data+SQL+бизнес-правила в одном классе; отдельно `User.php` вдобавок сам управляет `$_SESSION`/
  `$_COOKIE`: `securityAuthorize()` (631-652) и `authorize()` (594-620) в одном методе делают `$DB->get()` и тут
  же пишут 6 ключей сессии + `setcookie()`; `logout()` (743-750) руками разбирает `unset()` шести ключей сессии;
  `changePassword()` (910-922) сама решает, нужно ли обновить `$_SESSION['password']` текущего залогиненного
  пользователя. `User::create()` (447-506) заодно выступает и репозиторием, и сервисом регистрации (валидация
  уникальности логина/email, генерация verification-кода, назначение роли, отправка email) — всё в одном методе
  модели.
- **Отсутствие транзакций вокруг связанных записей.** `DataBase`/`MySqlDriver` предоставляют
  `startTransaction`/`commitTransaction`/`rollbackTransaction`, но по коду приложения (`Models/*`, `App.php`)
  реальных вызовов этих методов нет вообще. Самый рискованный пример — `User::create()`
  (`User.php:466` — `INSERT` пользователя, затем `getRolesObject()->addRole()` — отдельный `INSERT` в
  `Roles.php:115-123`, затем `sendVerificationCode()`/отправка email): если `addRole()` упадёт после того,
  как пользователь уже вставлен, в базе останется пользователь без роли — код это осознаёт лишь на уровне
  try/catch с логированием, но откатить уже вставленную строку некому. Похожий паттерн — `MQ::execute()`
  (`MQ.php:566-573`, обновление статуса задачи без транзакции перед выполнением бизнес-кода задачи).
- ~~**Двойная автозагрузка классов.**~~ Устранено на Этапе 1. Все файлы ядра переименованы из `*.class.php` в
  `*.php`, самописный `spl_autoload_register` из `core/bootstrap.php` удалён, а маппинг PSR-4 исправлен на
  `"Core\\": "core/lib/Core/"` — прежнее значение `"core/lib/"` было ошибочным, поскольку PSR-4 отбрасывает
  префикс `Core\` и заставляло composer искать классы в `core/lib/Helpers/...` вместо `core/lib/Core/Helpers/...`.
  Именно из-за этой ошибки маппинга и существовал второй автозагрузчик. Теперь автозагрузка одна — composer;
  при добавлении класса имя файла и namespace обязаны точно соответствовать пути.
- ~~**Нет центрального обработчика ошибок/исключений.**~~ Закрыто на Этапе 3: `Delta\Error\ErrorHandler`
  регистрирует `set_error_handler`/`set_exception_handler`/`register_shutdown_function`, а `Kernel` ловит любое
  исключение из экшена. Всё пишется в `core/log/error.log.php` через `Log::logToFile`.
  **Файлы журналов получают расширение `.php` и заглушку `<?php exit; ?>` в первой строке** — иначе журнал со
  стектрейсами, IP и логинами читался бы прямо по URL, поскольку каталог логов лежит внутри корня сайта.
  После переноса docroot в `public/` эту защиту можно будет снять.
- **MQ-очередь: race condition при взятии задачи + отсутствие супервизора воркеров.** `MQ::execute()`
  (`MQ.php:510-573`) — классический check-then-act без блокировки: `SELECT` статуса задачи (512), проверка
  `in_progress` в PHP (546), и только потом `UPDATE ... SET in_progress='Y'` (566-573) — ни `SELECT ... FOR
  UPDATE`, ни `GET_LOCK()`, ни транзакции между шагами нет, так что два воркера, стартовавшие почти одновременно,
  оба могут пройти проверку и взяться за одну и ту же задачу. Воркеры порождаются как независимые процессы через
  `exec('(php -f .../threadsWorker.php ... & ) ...')` (`MQ.php:773`, `core/cronTasks/threads.php:25`) без
  сохранения PID и без перезапуска при падении; подсчёт живых воркеров идёт хрупким парсингом `ps -awx | grep
  ...` (`MQ.php:761`, `getCountWorkers()`) — платформенно-зависимо (Linux-only) и падает молча при любом
  расхождении формата вывода `ps`. Единственный механизм восстановления — `searchAndFixStuckTasks()`
  (`MQ.php:805+`), который пассивно возвращает в очередь задачи, зависшие дольше `STUCK_TIME` (15 минут) — то
  есть упавший воркер обнаруживается по таймауту, а не активно.
- **Админка: контроль доступа централизован (Этап 4), но дублирование инициализации осталось.**
  Проверка прав теперь выполняется ровно в одном месте — `admin/inc/bootstrap.php`, который подключают все
  страницы админки. Там же заданы два списка: `$publicAdminPages` (доступны без прав: вход, выход, регистрация)
  и `$adminOnlyPages` (требуют полных прав администратора, а не просто доступа в панель). **Новая
  admin-страница по умолчанию закрыта** — забыть проверку больше нельзя. Именно этой централизации не хватало:
  `admin/ajax/threads.php` подключал бутстрап напрямую, минуя проверку в `header.php`, и отдавал содержимое
  очереди задач анонимному пользователю.
  Осталось нерешённым: `admin/inc/bootstrap.php` по-прежнему создаёт второй объект `User` отдельным запросом,
  хотя `core/bootstrap.php` уже создал `$USER`; и у `admin/login.php` есть своя ветка входа через
  Telegram-виджет, которой нет в основном роутере. Оба пункта — на Этапы 5-6.
- **`DataBase` — хардкодный singleton без точки подмены для тестов.** `DataBase::getInstance()`
  (`DataBase.php:58-64`) создаёт `new self($driver)` при первом вызове и хранит в статическом поле; сеттера для
  подмены реализации в тестах нет (`setInstance` в кодовой базе не встречается). Конструктор при отсутствии явных
  параметров жёстко берёт `DB_HOST`/`DB_NAME`/`DB_USER`/`DB_PASSWORD` из глобальных констант — то есть любой тест,
  затрагивающий модель, реально стучится в MySQL, если не подменить константы окружения целиком. Это согласуется с
  тем, что единственный существующий тест, `tests/UserTest.php`, ничего не тестирует (`assertTrue(true, ...)` без
  единого обращения к `User`/`DataBase`), несмотря на неиспользуемый `use Core\Models\User as TestClass;`.
- **Несколько параллельных реализаций одного и того же клиента.** Помимо уже отмеченных выше Telegram-клиентов —
  фактически их четыре, а не два: `Telegram.php` используется только из `TelegramActions.php`, а сам
  `TelegramActions` нигде в проекте больше не вызывается (мёртвый код, ~770 строк на двоих); реально используются
  `Telegram2.php` (входящий webhook, `telegramHandler.php`) и `TelegramSender.php` (исходящие
  уведомления, `core/bootstrap.php:149,152`, `MQTasks.php`) — два живых клиента, дублирующих HTTP-логику
  Bot API и никак не переиспользующих код друг друга. Похожая картина с именем "Request": в проекте три разных
  класса с этим именем — `ExternalServices/Request/Request.php` (импортируется в `bootstrap.php:23`, но
  нигде не вызывается — мёртвый `use`), `ExternalServices/RequestOLD.php` (мёртвый код целиком) и
  `Core\Api\Request` (реально используется в `ApiController.php:59,110,143` как обёртка над входящим
  запросом — по смыслу это вообще не то же самое, что первые два HTTP-клиента). При расширении интеграций стоит
  явно решить, какой из живых клиентов канонический, и удалить мёртвые файлы, а не добавлять пятый вариант.
